# Context Budget

[English](README.md) | [Русский](README.ru-RU.md)

Скилл, который минимизирует **расход входных токенов** при кодинге, отладке, ревью и исследовании кода: упаковывает много действий в один ход и жёстко ограничивает объём, который любой инструмент может вернуть — не пропуская обязательные проверки корректности.

**A/B-тест на трёх типах задач — сборка сайта из 8 страниц, багфикс в маленьком CLI и аудит из 12 вопросов по монорепо на 132 файла: на 31–54% меньше токенов и на 23–60% меньше времени со скиллом.**

## Почему входные токены растут

Транскрипт пересылается как вход на каждом ходу и каждый раз оплачивается заново. Три вещи растят его безвозвратно — ничего не удаляется до самой компакции:

1. **Результаты инструментов** — каждое чтение файла, вывод каждой команды остаются в контексте до конца сессии.
2. **Собственные сообщения модели** — каждая строка нарратива, пересказ плана, вставленный сниппет и подробный ответ заново оплачиваются на каждом следующем ходу.
3. **Сами инструкции** — ещё одна причина держать скилл плотным.

Дополнительные ходы и лишние байты усиливают друг друга: каждый новый ход заново оплачивает всё, что уже в контексте, а каждый раздутый результат заново оплачивается каждым последующим ходом. Поэтому скилл требует **оба рычага одновременно**:

- **Меньше ходов** — упаковывать максимум независимых действий в каждый ход (спекулятивные цепочки мультидействий, запись всех файлов одним сообщением).
- **Меньше байт за ход** — жёсткий лимит на то, что инструмент может вернуть (чтения ~150 строк, ограниченный поиск, `tail -n 30` для вывода команд).

## Что делает скилл

| Секция | Правило |
|---|---|
| Модель стоимости | Стоимость ≈ (байты в контексте) × (осталось ходов). Работать надо по обоим множителям, менять один на другой нельзя. |
| Бюджеты ходов по типу задачи | Поиск факта 1–2 инструментальных хода, ревью 2–3, багфикс 3, фича 4–6, незнакомое огромное репо +1. Плюс правило «без регрессий»: любое правило, которое добавит ход, не нужный этой задаче, — пропускается; сам протокол читается один раз и никогда не перечитывается. |
| Правило хода | Спекулятивные цепочки: предсказать всю последовательность и выдать её пакетом (все Write вместе, все чтения вместе); для набора вопросов — все символы в одну альтернацию `rg`. При первом сюрпризе — откат в одношаговый режим. Запрещено между действиями: статусы, пересказ плана, «думанье вслух». |
| Жёсткие лимиты вывода | Найденная строка поиска — уже ответ: открывать файл «на подтверждение» — дефект. Чтения ≤ ~150 строк (300 = дефект), `rg -m 20` / `head -n 40`, сначала `git diff --stat`, `2>&1 \| tail -n 30`, никогда полные логи/локфайлы/минифицированное/JSON-дампы, ни один результат больше ~10k токенов. |
| Делегировать только выше порога | Субагент переоплачивает свой промпт на каждом своём запросе, поэтому делегировать только выше ~2000 строк / ~15 файлов или когда цель неизвестна. Никогда два агента на один вопрос, никогда не делегировать то, что решает один `rg`. Делегировать факты, а не контент под правку. |
| Додумать, потом выдать | Один проход на файл: импорты, обработка ошибок, тесты — тем же Write. Никогда не перечитывать только что написанное. Все правки, вытекающие из новых результатов, — в один следующий ход. |
| Проверить один раз | Правки: один ход проверки с лимитом вывода, без незапрошенных смоук-тестов. Поиск: ответ и есть проверка. |
| Гигиена сессии | Переиспользовать, не перезапрашивать. `path:line` вместо цитат. Две неудачные попытки — выводить причину заново, а не латать третий раз. Долгие сессии: один notes-файл, переживающий компакцию. |
| Непреложное | Плотность не важнее корректности: не угадывать содержимое файлов, не пропускать тесты; недочитанное чтение, из-за которого придётся перечитать, дороже правильного. |

## Установка

Скилл — это обычный `SKILL.md` (плюс опциональные метаданные интерфейса), без зависимостей и скриптов. Нативная поддержка **Agent Skills** есть в ZCode, Claude Code и Codex CLI. Для агентов на правилах ставится как постоянное правило.

### ZCode

```bash
git clone https://github.com/SoftArax/Context-Budget.git
cp -r Context-Budget ~/.zcode/skills/context-budget
```

На уровне пользователя (во всех рабочих папках). Для одного проекта — скопируйте в `<проект>/.zcode/skills/context-budget`.

### Claude Code

```bash
git clone https://github.com/SoftArax/Context-Budget.git
cp -r Context-Budget ~/.claude/skills/context-budget
```

Формат тот же (`SKILL.md` с frontmatter `name`/`description`) — Claude Code подхватит скилл автоматически и будет применять по мере уместности; можно вызвать и явно через `/context-budget`. Для одного проекта — в `<проект>/.claude/skills/context-budget`.

### Codex CLI

```bash
git clone https://github.com/SoftArax/Context-Budget.git
cp -r Context-Budget ~/.codex/skills/context-budget
```

`agents/openai.yaml` добавляет метаданные интерфейса (отображаемое имя, краткое описание, промпт по умолчанию).

### Cursor

Agent Skills не поддерживаются; ставим как постоянное правило проекта:

```bash
git clone https://github.com/SoftArax/Context-Budget.git
mkdir -p .cursor/rules
{ printf -- '---\ndescription: Minimize input-token cost: many actions per turn, hard-capped tool output\nglobs: \nalwaysApply: true\n---\n\n'; tail -n +5 Context-Budget/SKILL.md; } > .cursor/rules/context-budget.mdc
```

Закоммитьте правило в репозиторий, чтобы оно было у всей команды.

### Windsurf

```bash
git clone https://github.com/SoftArax/Context-Budget.git
mkdir -p .windsurf/rules
tail -n +5 Context-Budget/SKILL.md > .windsurf/rules/context-budget.md
```

### Gemini CLI

Добавьте тело скилла в свой контекстный файл:

```bash
git clone https://github.com/SoftArax/Context-Budget.git
tail -n +5 Context-Budget/SKILL.md >> ~/.gemini/GEMINI.md
```

### Cline / Roo Code

```bash
git clone https://github.com/SoftArax/Context-Budget.git
mkdir -p .clinerules   # Roo Code: .roo/rules/
tail -n +5 Context-Budget/SKILL.md > .clinerules/10-context-budget.md
```

### Всё, что читает AGENTS.md

Вставьте тело `SKILL.md` (всё после frontmatter) в свой `AGENTS.md` — скилл написан агент-независимо и работает везде, где модель читает инструкции проекта.

> Примечание: секция про делегирование субагентам работает только там, где субагенты есть. В остальных агентах она просто ничего не делает.

## Результаты A/B-тестов

Каждую задачу выполняли два одинаковых агента на одной модели в побайтово идентичных копиях одной фикстуры, параллельно: один со скиллом, другой без. Токены и число вызовов взяты из служебных записей об использовании, а не из самоотчётов. Во всех прогонах обе стороны дали корректный результат (тесты проходят / все 12 ответов верные).

| Задача | Токены со скиллом / без | Вызовы инструментов | Время |
|---|---|---|---|
| Багфикс — падающий тест в Node CLI из 9 файлов | **127,8k / 279,4k** (−54%) | 9 / 19 (−53%) | 67с / 167с (−60%) |
| Аудит — 12 вопросов по монорепо из 132 файлов | **162,7k / 235,0k** (−31%) | 7 / 10 (−30%) | 92с / 120с (−23%) |
| Сборка — законченный сайт из 8 страниц | ~−50% входных токенов | меньше ходов | — |

**Почему это работает.** Стоимость ≈ (байты в контексте) × (осталось ходов), поэтому давить нужно на оба множителя сразу: пакетные действия сокращают ходы, жёсткие лимиты — остаток каждого хода. Каждая строка, не попавшая в контекст, — это строка, которую не переоплатит каждый последующий ход.

**Почему прошлые версии регрессировали.** Первый вариант выигрывал на сборке, но крупно проигрывал на аудите (+72% токенов): он делегировал субагенту то, на что хватало одного `rg`, и заново открывал файлы, которые уже нашёл. Именно от этого защищают бюджеты ходов по типу задачи, правило «найденная строка — уже ответ» и порог делегирования (~2000 строк / ~15 файлов). Протоколу прямо запрещено делать задачу дороже, чем она была бы без него.

## Замечания и честные ограничения

- Скилл сокращает **ходы модели/инструментов**, а не клиентские HTTP-запросы: отправлять параллельные вызовы инструментов одним или несколькими API-запросами решает клиент.
- Лимиты подобраны ради экономии; на действительно огромных файлах используйте точечные чтения `offset/limit` или извлечение через shell вместо чтения целиком.
- Плотность никогда не важнее корректности — протокол явно разрешает дополнительные ходы и большие чтения, когда проверке они действительно нужны.
